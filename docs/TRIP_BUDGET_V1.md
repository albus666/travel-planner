# 配额控制、重规划和多日游 v1

本版增加 `/maps/usage`、`/plan/replan`、`/plan/multi-day`。复用原来的 RAG 证据规划和百度适配器，原 `/ask`、`/search`、`/plan` 不变。新规划仍受 `RAG_MAPS_ENABLED` 开关控制。

## 百度调用控制

所有真实百度请求先走 SQLite 原子预算预留，同服务器、同数据库的进程/AK 共享计数。默认路径 `var/maps.sqlite3`，可用 `BAIDU_BUDGET_DB` 指定；重启不清零。AK 不写入数据库。

- 地点搜索和输入提示共享每日80次预算；逆地理编码200次；其余每服务1000个单位。是项目保守预算，不是对平台配额的实时读取。
- 矩阵按 origins×destinations 计数；普通请求一次一个单位；失败请求也计入已预留用量。
- 账号当天用量按北京时间日期切分；其他机器/应用用同一百度账号的请求不在本地计数内。多机部署需共享限额服务后才能声称账号全局限制。
- 各服务请求预留间隔至少0.55秒，最多等待2秒；队列满直接返回 `not_queried/local_rate_limit_queue_full`，不自动重试。
- 路线和矩阵缓存5分钟，地点/地址/坐标缓存24小时；缓存命中不耗本地调用预算，并保留原 fetched_at，返回 cache_hit。失败不写缓存，无过期缓存兜底。
- `GET /maps/usage` 返回当日本服务计数。可用环境变量 `BAIDU_DAILY_PLACE`、`BAIDU_DAILY_REVERSE`、`BAIDU_DAILY_MATRIX` 等设置更低预算，0表示禁止缓存之外的新请求。路线例如 `BAIDU_DAILY_DIRECTIONLITE_V1_DRIVING`。

预算耗尽或存储不可用会停止发送请求，不把失败当成零分钟。

## 有界重规划

`POST /plan/replan` 请求：`{"route": 原 /plan/with-routes 请求, "max_replans":3}`。

流程：原证据草案 → 查交通并验时间 → 如超时，移除排序最后的一个非必去景点 → 重新计算新路线与时间。最多三轮，可设置0关闭。复用缓存，不跑全量矩阵（原 optimize_order 默认false）。每轮保留状态、已移除景点与路线证据。

必去、游览时长、结束时间不会被自动放宽。只剩必去、只剩一站或仍超时时返回冲突；工具失败、证据不足、配额不足时不做盲目重试。不会重新选景点填补刚移除的站点。

这是确定性的约束修复，不增加 LLM planner。尚不支持自动缩短停留、改交通方式、把景点跨日搬移或替换目的地。

## 多日游

`POST /plan/multi-day` 请求：`{"days":[第一天的路线规划请求,第二天的路线规划请求],"max_replans_per_day":3}`。

支持洛阳连续1–7天，每个每日 plan.days=1，日期显式填写。每一天分别提供偏好、节奏、交通、起终点、时间窗口、游览时长及必去/排除条件。前一天终点坐标必须等于后一天起点（例如已确认酒店）；未安排的跨夜转移不自动猜测。

服务自动预留后续日期必去景点，将已安排景点加入后续排除列表，避免重复。每一天复用有界重规划。某天失败或需澄清时停止，返回 `unplanned_days`，不把后续日期标为成功。

首版是逐日有证据的计划组合，沿用七景点候选池；不是任意城市/无限候选的全局最优旅游规划。建议必去/排除通过结构化字段填写；不支持只输入一句自然语言就自动补全整段旅行和酒店。样例见 `rag/client/examples/trip_two_days.json`，执行前更新出行日期及酒店坐标。

```powershell
python rag/client/maps_query.py --url http://127.0.0.1:8100/plan/multi-day --json-file rag/client/examples/trip_two_days.json
```

仍未核实景区开放、预约、预算、体力、酒店库存和未来交通。所有时刻都是查询时交通估算叠加用户时长得到的草案。
