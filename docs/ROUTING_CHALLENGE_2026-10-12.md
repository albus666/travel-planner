# 路由v2冻结与新增30题合成挑战

用户要求代理生成下一批问题，因此本批是合成挑战集，不是来自真实用户的独立盲测。题目和预期store标签在运行前固定，与已有case文件无完全相同问法；生成者已知现有规则和数据边界，不能据此证明真实分布泛化。标签仍待用户审核。

## 冻结范围

`rag/eval/baselines/routing_v2_frozen/` 保存服务器实际路由源码、服务入口、回答源码、检索源码、原型及阈值配置、58题及结果、此前25/73题在线回归记录。本批题目和SHA-256也在快照中。未归档.env或密钥；阈值仍为0.60，分差仍为0.06，语义路由仍启用。本轮未改服务源码、Prompt、规则、阈值、排序或重启服务。

12题实体项包含8题完整景点名和4题缺失/歧义/未知/多景点输入。4题后者均无法唯一解析，实际返回请求完整单个景点名的答复，没有返回景点票价记录。`route=sql_ticket`是处理入口，不意味着已执行景点票价SELECT；目录解析与最终票价查找应分开理解。

不要将本轮结果写成“30题全通过”或“系统准确率100%”。单store匹配仅验证路径选择；它不自动验证引用、事实、时效或回答完整性。

## 已暴露的能力缺口

27—30题同时要求ticket_raw和RAG内容。当前Intent只能返回一个store，边界闸将这些题送到RAG。回答可给路线、历史或优待等文本，但无法获得SQL里的票价原文。例如27、28、30题表示片段未提供票价，尽管数据库实际有ticket_raw；29题回答了优待与停车设施，也没有提供票价原文。

这是单路径能力缺口，不能算成普通单store假阳性/假阴性，也不能因为部分回答有引用就计为完整成功。评审时单独检查是否说明只完成部分问题、是否请求拆分。下一步可决定先明确提示用户拆分，或单独实现双store组合；本轮不扩充架构、不加入LLM分类或LangGraph。

## 人工评审与复现

- 题目及运行前标签：`rag/eval/cases/routing_challenge_v1.jsonl`。
- 人工阅读文件：`rag/eval/reports/routing_challenge_v1_run1.md`，逐题保留问题、预期行为、完整回答、引用、取回片段和评分空位。
- 结果与用户评分：`rag/eval/reports/routing_challenge_v1_run1.json`，human_review已逐题填写；原始未评分记录保留为 `_unreviewed.json` 和 `_unreviewed.md`。
- 运行器：`rag/eval/runners/run_routing_challenge.py`，拒绝覆盖快照/报告，运行后核验冻结源码未变化。

按pass/fail/na评分事实、引用、景点隔离、拒答、时效、要点覆盖；拒答正确看是否该答则答、该拒则拒。失败归因分路由、实体、SQL、生成、数据或能力缺口。不要仅根据status自动判断拒答正确，也不要沿用先前25题人工分数。

本地3项评测统计测试通过，确认混合题不会算单路径成功、不混入票价FP/FN分母，且路径正确不会自动产生回答质量通过分。原23项服务测试、25题上下文和73题检索回归结果保留在冻结快照，本轮没有服务改动，因此未重复整批回归。

服务器复现需设置PYTHONPATH=rag，在现有.venv执行：

```bash
.venv/bin/python rag/eval/runners/run_routing_challenge.py \
  --cases rag/eval/cases/routing_challenge_v1.jsonl \
  --output rag/eval/reports/routing_challenge_v1_run2.json \
  --freeze rag/eval/baselines/routing_v2_run2
```

运行会使用现有回答模型，有正常API调用成本；需要语义编码时复用既有BGE-M3模型。输出和freeze路径须为新路径。本集应保留为挑战/回归集；以后若依据它调整规则，就更不能把它当盲测集。
